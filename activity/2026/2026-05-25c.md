## Preset seeding visible on Budgets and Categories pages

### Problem
`seedPresetsIfEmpty()` was only called from `app/page.tsx` (dashboard). If a user
navigated directly to `/budgets` or `/categories` without first visiting the dashboard,
the 30 preset categories and 25 preset budgets would not yet exist in their account
and both pages would appear empty.

### Fix
Added `await seedPresetsIfEmpty(user.id)` to the server component of both pages:
- `app/budgets/page.tsx` — presets now seed before the budget list query runs
- `app/categories/page.tsx` — presets now seed before the category list query runs

The function is idempotent (exits immediately after a single DB count if already
seeded), so the extra call on pages that are visited after the dashboard costs one
fast count query and nothing else.

### Result
The 30 preset categories and 25 preset budgets from `lib/seed.ts` are now visible
on the first visit to **any** of the three seeded pages: Dashboard, Budgets, or
Categories — whichever the user opens first.

## Design conversation — transaction model

Discussed the fundamental limitations of the current `expenses`-only model:

- `expenses` table name and all its enums assume money-out only
- `amount` has no direction — always treated as a debit
- No model for income, chargebacks, refunds, transfers, or bank fees
- Budget math (`SUM(amount)`) breaks when credits need to reduce spending
- `bank_entries` has the same directional ambiguity

**Two candidate models discussed:**
- **YNAB-style**: income is assigned to budget envelopes before spending; chargebacks
  go back into the source category. More structured, requires "To Be Budgeted" concept.
- **Ledger-style**: every transaction has a type (debit/credit/transfer) and a signed
  amount; income categories track inflow; net = income − expenses over any period.
  Simpler for aggregation math.

**No changes made yet.** Decision on which model to adopt is pending before any
schema migration work begins.
