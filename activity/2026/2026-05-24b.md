## Phase 3 — Drizzle ORM, Auth, PWA Dashboard

**Goal:** Replace ad-hoc Supabase JS queries with Drizzle ORM, add Supabase SSR auth,
build the full PWA UI: login, dashboard, review queue, expense list, budget manager.

- [x] Installed runtime deps: `drizzle-orm`, `postgres`, `@supabase/ssr`
- [x] Installed dev dep: `drizzle-kit` (schema introspection + migration tooling only,
      never imported in application code)

  [note] `@supabase/ssr` is required for Next.js App Router auth — it handles cookie
  management across Server Components, Route Handlers, and Middleware correctly.
  `@supabase/supabase-js` alone cannot do this in App Router.

### Database layer
- [x] lib/db/client.ts
  ```typescript
  const sql = postgres(process.env.DATABASE_URL!, { prepare: false });
  export const db = drizzle(sql, { schema });
  ```
  `prepare: false` is mandatory for the transaction-mode pooler (port 6543).
  Omitting it causes "prepared statement does not exist" errors under any concurrency
  because PgBouncer does not maintain prepared statement state between connections.

- [x] lib/db/schema.ts — hand-written to mirror all 4 migrations exactly
  Critical rules encoded in CLAUDE.md:
  - `expenses.amount` must NOT use `.notNull()` — nullable by migration 20240004
  - `expense_source` enum needs all 4 values: telegram, shortcut, manual, csv
  - Storage bucket is named `receipts` — upload paths must not include `receipts/` prefix

- [x] drizzle.config.ts — points to lib/db/schema.ts, dialect: postgresql

### OCR extraction
- [x] lib/ocr.ts — extracted OCR logic from app/api/telegram/webhook/route.ts
  [decision] Extracted to lib/ocr.ts so the retry-ocr API route and the webhook route
  share the same implementation without duplication. The webhook route now imports
  `runOcr` from lib/ocr.ts.

### Auth layer
- [x] lib/supabase/server.ts — `createSupabaseServerClient()` using `@supabase/ssr`
  Reads/writes cookies via Next.js `cookies()` API. Used in Server Components and
  Route Handlers.

- [x] lib/supabase/middleware.ts — `updateSession()` for proxy.ts
  Refreshes the Supabase session token on every request so it never expires silently.

- [x] proxy.ts — route protection
  [bug] File was initially named `middleware.ts` following the Next.js 13/14 convention.
  Next.js 16 deprecated this — the file must be named `proxy.ts` and the exported
  function must be named `proxy`, not `middleware`. The build succeeded but emitted a
  deprecation warning on every deploy.
  [fix] Renamed middleware.ts → proxy.ts, renamed export.
  → see node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md

- [x] lib/auth.ts — `requireUser()` helper
  Used at the top of every Server Component and Route Handler that needs auth.
  Calls `supabase.auth.getUser()` and redirects to `/login` if no session.
  [decision] `getUser()` not `getSession()` — Supabase recommends getUser() for
  server-side auth checks because it validates the token with the server,
  not just the local cookie.

### API routes
- [x] app/api/auth/callback/route.ts — exchanges Supabase magic-link code for session
  Required for email OTP / magic-link flow. Supabase redirects to this route after
  the user clicks the email link.
  [note] The redirect URL `https://ledger-gules-seven.vercel.app/api/auth/callback`
  must be added to Supabase → Authentication → URL Configuration → Redirect URLs.

- [x] app/api/expenses/[id]/route.ts — PATCH (whitelist-based) + DELETE
  Patch whitelist: merchant, amount, currency, date, confirmed_category,
  category_id, notes, status. Any other key in the request body is silently ignored.

- [x] app/api/expenses/[id]/retry-ocr/route.ts — re-runs OCR on stored receipt URL
  Downloads the image from Supabase Storage, detects MIME type from URL extension,
  runs through lib/ocr.ts, updates the expense row, sets status → pending_review.

- [x] app/api/buckets/route.ts — GET (all) + POST (create)
- [x] app/api/buckets/[id]/route.ts — PATCH + DELETE
- [x] app/api/categories/route.ts — GET (all) + POST (create)

  [decision] No PUT/replace routes — PATCH only. The UI only ever updates individual
  fields, never replaces a whole record.

### UI pages
- [x] app/login/page.tsx — magic-link email auth (client component)
  Uses `createBrowserClient` from `@supabase/ssr` for client-side auth calls.
  `signInWithOtp` sends a magic link — no password management required.

- [x] app/page.tsx — dashboard (server component)
  Shows: pending-review banner with count + link to /review, budget cards grid,
  recent 5 expenses list.

- [x] app/review/page.tsx + app/review/ReviewCard.tsx
  ReviewCard is a client component — it manages local form state and calls PATCH API.
  [decision] On confirm: sets both `confirmed_category` (text) AND `category_id` (UUID FK).

  [decision] `category_id` is only set if an exact name match exists in the categories
  table — the app never auto-creates a category. If the user types a free-form category
  that doesn't exist yet, `category_id` remains null until they create the category.

- [x] app/expenses/page.tsx — full expense list grouped by date
  Day totals calculated client-side (server component renders them).
  Status badges colour-coded: amber (pending_ocr), blue (pending_review),

- [x] app/buckets/page.tsx + app/buckets/BucketsClient.tsx
  BucketsClient handles create/delete with optimistic `router.refresh()`.
  PERIODS array matches the budget_period enum exactly — any mismatch would be

- [x] app/error.tsx, app/loading.tsx + per-route error/loading for review, expenses, buckets

## Documentation System Design

**Goal:** Replace the notes/ToDo scratch file with a proper in-repo system that acts
as the project's issue tracker — replicating what teams get from Linear, Jira, or Notion
without any external dependency.

### Key decisions
- [decision] `activity/` directory replaces Linear/Jira/Notion as the issue tracker
  The chronological thread is the date, exactly as it is in professional issue trackers.
  Every piece of work — file created, decision made, bug fixed — is mentioned in the
  dated file for the day it happened.

- [decision] Date-based files (`YYYY-MM-DD.md`) as the primary chronological unit
  ISO 8601 sorts correctly in any file browser. Split by context (append b, c, d)
  when a day contains two unrelated bodies of work, not by clock time.

- [decision] `activity/phases/` for phase context files
  Created before the phase starts. Contains goal, scope, key constraints.
  Does NOT list tasks — tasks belong in `activity/ToDo.md`.
  References `activity/ToDo.md` for the task breakdown.

- [decision] `docs/build.md` as the 40,000-foot view
  One section per phase. Brief. Links to activity/ for full detail.
  Read by someone who wants to understand the whole application, not debug a bug.

- [decision] `notes/` remains gitignored as a personal scratch space
  `notes/claude_chat_history.md` and any personal working notes stay local.
  `/notes` was already in .gitignore.

- [decision] `playbook/` captures the methodology
  Will be transferred to its own repository: kevinchisholmja/playbook
  Contains the "how I build" philosophy — not project-specific.
