## `rules/` directory — 5 concern-scoped rule files

Created a `rules/` directory. Each file covers one concern so AI agents (and humans)
only need to read what's relevant. The root `CLAUDE.md` imports all five via `@`.

### `rules/code-style.md`
- No comments by default — only when WHY is non-obvious
- No multi-line comment blocks, no task references in code
- Scope discipline: no features, abstractions, or cleanup beyond the task
- TypeScript: strict types, no implicit `any`, infer from Drizzle schema
- File/function/constant naming conventions
- Error handling: validate at boundaries only, trust internals, early returns
- No dead code — delete unused code, don't comment it out

### `rules/security.md`
- `requireUser()` must be first line of every route handler / server component
- Every Drizzle query must have `WHERE user_id = user.id` — service role bypasses RLS
- Client split: Drizzle for DB, Supabase JS for auth + storage only
- Input validation: PATCH whitelist pattern — never spread `req.json()` into DB update
- Secrets: always env vars, never in code, never logged
- SQL injection: Drizzle parameterized queries only — no raw string interpolation

### `rules/api-conventions.md`
- Route file locations: `app/api/{resource}/route.ts` and `[id]/route.ts`
- Method semantics table: GET/POST/PATCH/DELETE → status codes + response format
- Mandatory handler pattern: requireUser → validate → query with user_id → return
- PATCH whitelist pattern (complete code example)
- Current route inventory (all `/api/*` endpoints)
- Phase A4 note: add `/api/transactions/[id]` alongside old route during transition

### `rules/database.md`
- The one rule: every query needs `WHERE user_id = user.id`
- Client split table: Drizzle vs Supabase JS vs Storage
- Drizzle patterns: select with join, insert returning, update returning, delete returning
- Schema conventions: UUID PKs, nullable columns, timestamps
- Migration rules: naming, IF NOT EXISTS, SQL Editor only, never modify applied migrations
- Phase A transition table: which tables exist, which are coming, which are going

### `rules/ui-standards.md`
- Colour table: blue-600 primary, navy sidebar, page backgrounds, amount colours
- Tailwind v4 import syntax
- Card and sidebar component patterns
- Currency formatting rule: always formatJMD()/formatCurrency() — never inline
- Form fields: always `<select>` from DB — never free text
- Safe area insets: inline style only (Tailwind v4 has no utility)
- Monospace numbers: `tabular-nums` on all financial amounts
- z-index stack table: FAB / nav drawer / tab bar / sidebar / sticky headers

## `.claude/settings.json` — project permissions and hooks

Written as the committed project-level settings (separate from `settings.local.json`
which contains early-project bootstrap permissions and stays gitignored).

### Permissions — deny list (hard blocks)
```
git push --force*
git push -f *
git reset --hard*
git clean -f*
git checkout -- *
rm -rf *
DROP TABLE*
DROP DATABASE*
TRUNCATE *
vercel --prod*
```

### Permissions — allow list
Covers: safe git (status/diff/log/add/commit/push to main), npm/npx, ls/find/grep,
mkdir, sed, vercel logs/env, gh CLI.

### Hooks
**`PostToolUse(Edit|Write)`** — TypeScript error check after every file edit:
```bash
npx tsc --noEmit 2>&1 | grep -E '^.*\.tsx?\([0-9]+,[0-9]+\): error' | head -8
```
This feeds TypeScript errors back to Claude immediately after an edit so problems
are caught before the next tool call rather than at the end of a session.

**`PreToolUse(Bash)`** — blocks destructive patterns at the gate:
Checks the command string for `push --force`, `reset --hard`, `DROP TABLE`,
`TRUNCATE`, `rm -rf` — exits with code 2 (blocking the tool call) if found.
