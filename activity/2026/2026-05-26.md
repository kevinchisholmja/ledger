## Google Sheets ledger analysis

Reviewed the existing financial tracking spreadsheet at the user's Google Drive link.

### Spreadsheet structure identified
- Multi-account Quicken-style register (BNS Savings, CIBC Checking, Cash, Lasco Pay Credit Card)
- Columns: Account · Invoice Date · Paid Date · Num · Name · Sub-Name · Category ·
  Details · Mode of Payment · Clr · Date Clrd · DEBIT · CREDIT · Account Balance ·
  Cleared Balance · BALANCE · Inv./State./Doc. · Receipts
- Separate income and expense category lists
- Sinking funds (Car Fund, Tax Fund) with progress tracking
- Annual budget vs actual table (Jan–Dec columns, Total, Average)
- Goals section per account (% to $1M)

### What was identified as good (keep)
- True double-entry: separate DEBIT and CREDIT columns
- Two dates per transaction (Invoice Date + Paid Date)
- Cleared vs uncleared balance (bank reconciliation)
- Reference numbers (check #, invoice #, wire ref)
- Transfers modeled as two-sided entries (SENT + RECEIVED)
- Payees as a named concept (Name + Sub-Name)
- Income categories explicitly separated from expenses
- Sinking funds (aligns with Goals page)
- Budget vs actual with monthly columns

## Architecture decision: YNAB + Quicken hybrid

**Decided and documented in `docs/SPEC.md`.**

### Model chosen
- **Data layer:** Ledger-style — every transaction has direction (debit/credit), type, account, and two dates. Pure record of what happened.
- **Budget UI:** YNAB-style — income flows to TBB; user assigns TBB to envelopes; Available = Assigned + Refunds − Spent
- **Register UI:** Quicken-style — per-account transaction register, running balance, cleared/reconciled

### How chargebacks and refunds work
- Refunds return to the expense category they came from (not to TBB)
- Only genuinely new money (salary, rental, commission) goes to TBB
- Linked to original transaction via `original_transaction_id` FK

### TBB (To Be Budgeted) — agreed to add
TBB = SUM(all income credits ever) − SUM(all budget_assignments ever)
TBB must never go negative — the UI blocks assignments that exceed it.

### Five teardown points agreed
1. `expenses` table → `transactions` (direction + type + two dates + cleared/reconciled)
2. `bank_entries` → replaced by `transactions` with source='csv' and cleared=true
3. Add `payees` table (Name + Sub-Name, default category/budget learning)
4. Extend `categories` with `type: 'expense' | 'income'`
5. Add `budget_assignments` table for TBB → envelope flow

## /register page (Phase A2 debugging tool)

**`app/register/`** (new route) — Quicken-style account register table.

### Purpose
A live debugging register that mirrors the Google Sheets layout. During the Phase A
migration (expenses → transactions), the user can open `/register` and instantly spot
which transactions have gaps in Category, Budget, Account, etc.

### Columns
Account · Paid Date · Invoice Date · Ref # · Payee · Category · Budget ·
Memo/Notes · Mode · Clr · DEBIT · CREDIT · Balance · Receipt

### Phase A2 state
Reads from `expenses` table (current data). Columns that don't exist yet:
- Account → `─` (Phase A3: joins to bank_accounts via account_id)
- Invoice Date → `─` (Phase A3: new column on transactions)
- Ref # → `─` (Phase A3: new column on transactions)
- CREDIT → `─` (Phase A3: credit transactions)

Amber notice banner explains the placeholder columns. Running balance computed
from sorted rows (cumulative debit total). Click any row to expand detail.
Totals footer: DEBIT total · CREDIT total · final balance.

### Implementation
- `app/register/page.tsx` — server component, queries expenses + categories + buckets
- `app/register/RegisterClient.tsx` — client component, full table with click-to-expand
- All 8 existing sidebars updated to include Register (▦) between Transactions and All Accounts
