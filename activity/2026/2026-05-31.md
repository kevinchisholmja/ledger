# 2026-05-31 — Supabase Connection Investigation + v0.dev Sandbox Constraints

Activity log for May 31st documenting the investigation into connecting the
existing Supabase backend to the v0.dev preview environment.

---

## Investigation — v0.dev Sandbox + Existing Supabase Backend

### Problem
The v0.dev preview showed "Supabase is not configured. Please add environment
variables." on the `/login` page, despite the Vercel project already having
Supabase connected (17 environment variables visible in the Vercel dashboard).

### Root cause
v0.dev runs the app inside a sandboxed Linux VM. Environment variables from the
Vercel project are NOT automatically injected into that sandbox — they live at
`/vercel/share/.env.project` and must be explicitly sourced.

- [bug] `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` were
  missing from the sandbox runtime, causing `createBrowserClient` to receive
  `undefined` and the login page to surface the configuration error banner.
- [fix] Created `.env.local` in the project root, populated from
  `/vercel/share/.env.project`, which Next.js dev server automatically sources.

### Further constraint — iframe cookie blocking
Once env vars were in place, the login page rendered correctly, but the v0
sandbox iframe blocks third-party cookies. This means:
- Google OAuth redirect flow is blocked (`This content is blocked` screen).
- Magic link email delivery and redirect callbacks are blocked.
- Client-side `signInWithPassword` succeeds and returns a valid session, but
  the session cookie set by `createBrowserClient` is not readable by server-side
  middleware on subsequent requests (third-party cookie isolation).

[decision] The v0.dev sandbox is not a viable environment for testing the full
auth flow. Development and testing of auth-dependent features should be done
against the production deployment at `ledger-gules-seven.vercel.app`.

### Dev-login experiment (added and reverted)
A temporary email/password dev login was added to work around the above:
- `app/login/page.tsx` — added password fields + "Set Password" / "Sign In" buttons.
- `app/api/dev/set-password/route.ts` — Supabase admin API to set password for
  existing Google OAuth user.
- `app/api/dev/set-session/route.ts` — server-side session sync attempt after
  client-side sign-in, to work around cookie isolation.
- `lib/supabase/middleware.ts` — temporary bypass for `vusercontent.net` host.

All of the above were reverted. The login page is restored to Google OAuth +
magic link only. The middleware bypass is removed.

[note] The `signInWithPassword` call itself worked — logs confirmed a valid
access_token was returned — but the cookie isolation prevented the middleware
from recognising the session on redirect.
