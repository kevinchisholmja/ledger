## Ledger — Agent Briefing

Read `docs/SPEC.md` before touching any code. Everything below is a summary — SPEC.md is the authority.

---

### What this project is

A personal finance PWA for a single user in Jamaica (JMD currency). It is not a bank aggregator — Jamaica has no open banking APIs. Every transaction enters through one of three manual channels: Telegram bot (receipt photo/PDF), iOS Shortcut (share sheet), or web upload (browser FAB). Claude Vision extracts structured data from receipts so the user never types amounts manually.

The architecture is a **YNAB + Quicken hybrid**:
- **Data layer**: ledger-style — every transaction has a direction (debit/credit), type, account, and two dates. A pure record of what happened.
- **Budget UI**: YNAB-style — income flows to "To Be Budgeted" (TBB); user assigns TBB to envelopes. Available = Assigned + Refunds − Spent.
- **Register UI**: Quicken-style — per-account transaction register, running balance, cleared/reconciled status.

Double-entry bookkeeping is enforced as a **database constraint**, not a UI layout. The app never shows T-accounts to the user — it looks like a modern consumer finance app. The classical accounting view (Chart of Accounts, General Ledger, Trial Balance) lives only in a planned `/reports` section for the accountant.

### What has been built (Phases 1–7)

The app is fully functional today. A user can:
- Submit receipts via Telegram, iOS Shortcut, or web upload → Claude Vision OCR → structured data
- Review and confirm pending transactions (set category, budget)
- View all transactions in a list with inline editing
- View a Quicken-style register at `/register` (currently reading from `expenses` table)
- Manage bank accounts, budget envelopes, and categories (all with preset seeding)
- Use the app on mobile (bottom nav + drawer) or desktop (sidebar)
- Track multi-year savings goals and a YNAB-style monthly plan

The codebase is clean, fully TypeScript, Tailwind v4, Next.js 16 App Router with Drizzle ORM against Supabase Postgres.

The documentation is comprehensive: `docs/SPEC.md` (master spec), `docs/architecture.md`, `docs/build.md`, `docs/runbook/database.md`, and a `rules/` directory of five concern-scoped files that the `CLAUDE.md` imports.

### The core problem and why we are rebuilding

The current `expenses` table was built with one assumption: every record is money going out. That assumption is baked into every layer — `amount` is always positive, there is no `direction` column, budget math only works for debits, the OCR pipeline is wired for receipts.

A transaction is not always an expense. Income, transfers, refunds, chargebacks, bank fees, and interest all need to be modeled. The UI already says "Transactions" — the database is wrong.

We are rebuilding the data model in phases (**Phase A**) while keeping the app functional throughout. The old `expenses` table stays live until Phase A6. Every phase is a separate commit.

---

### Decisions that are locked in — do not revisit

| Decision | What was chosen |
|---|---|
| `account_id` during migration | `NOT NULL` always. Migrated rows assigned to an "Unassigned" sentinel account. User re-assigns from the register. |
| Liability accounts | Extend `bank_accounts.type` with `credit_card`, `mortgage`, `loan`. No separate table. Balance sheet splits by WHERE clause. |
| TBB carry-forward | Carries month-to-month. Plan page is always monthly (period selector removed in Phase A5). |
| Double-entry in the UI | Never shown to the user. DB constraint only. T-accounts appear only in `/reports`. |
| Accrual vs cash | Store both `date` (paid) and `invoice_date` (obligation). Cash basis is default (Jamaica IT01). |
| Transaction entry forms | Type-aware — form morphs by transaction type. Phase A5. |
| Chargebacks / refunds | Return to the originating expense category, NOT to TBB. |
| Transfers | Single form creates two rows linked by `transfer_pair_id`. |

### What is about to happen: Phase A1

**Scope:** Create the v2 DB tables alongside the existing ones. No existing data is touched. The running app is unchanged.

**Four tasks:**

1. **Migration SQL** — `supabase/migrations/20240013_create_transactions_payees_assignments.sql`
   - `CREATE TABLE transactions` (full schema in `docs/SPEC.md §5.1`)
   - `CREATE TABLE payees` (§5.2)
   - `CREATE TABLE budget_assignments` (§5.3)
   - `ALTER TABLE categories ADD COLUMN type text NOT NULL DEFAULT 'expense'` (§5.4)
   - All with `IF NOT EXISTS`
   - Applied via Supabase Dashboard SQL Editor → project `evdbqegscpeaabzzcwvw`

2. **Drizzle schema** — `lib/db/schema.ts`
   - Add `transactions`, `payees`, `budgetAssignments` table definitions
   - Add `type` column to `categories`
   - Infer and export the new TypeScript types

3. **Income preset categories** — `lib/seed.ts`
   - Add 7 income-type categories to the preset list: Salary, Rental Income, Commission, Dividends, Interest Earned, Refund/Reimbursement, Other Income
   - These have `type = 'income'` and are only seeded if not already present (name-diff approach)

4. **Update `lib/db/CLAUDE.md`** — reflect the new tables and type exports

**What "done" looks like:**
- Migration applies cleanly with no errors
- `npx tsc --noEmit` passes with zero errors
- The running app is completely unchanged (no UI changes, no route changes)
- The new tables exist in Supabase but are empty
- `lib/db/schema.ts` exports types for all new tables

### Rules that are never optional

```typescript
// 1. Auth first — always the very first line
const user = await requireUser();

// 2. Every query scoped to the user
.where(eq(table.user_id, user.id))

// 3. Confirming a transaction sets three fields (v1 model, until Phase A4)
confirmed_category (text) + category_id (UUID) + bucket_id (UUID)
```

**PATCH routes:** always use the explicit field whitelist pattern — never spread `req.json()` into a DB update.

**No comments** unless the WHY is non-obvious. No multi-line comment blocks. No task references in code.

**TypeScript:** strict throughout. No `any`. Infer types from `typeof table.$inferSelect`. No `as unknown as X`.

**Currency:** always `formatJMD()` or `formatCurrency()` from `lib/format.ts`. Never inline.

**Category/Budget fields:** always `<select>` from DB. Never a free-text input.

### What comes after Phase A1

- **Phase A2**: Already done — the `/register` page is built and reading from `expenses`
- **Phase A3**: Migrate data — copy `expenses` → `transactions` (direction=debit, type=purchase), assign to "Unassigned" sentinel account
- **Phase A4**: Rewrite all API routes and queries to read from `transactions` instead of `expenses`
- **Phase A5**: New features — type-aware entry forms, income entry, transfer UI, TBB panel on Plan page (monthly-only revamp), per-account register, payee autocomplete
- **Phase A6**: Drop `expenses` and `bank_entries`
- **Phase B**: `/reports` section — Chart of Accounts, General Ledger, Trial Balance, Income Statement, Balance Sheet, Jamaica IT01 helper
